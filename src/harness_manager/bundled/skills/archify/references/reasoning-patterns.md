# Structured reasoning patterns

读取与当前问题匹配的一节. 每种模式都从真实问题和可信输入开始, 结构只服务于下一次判断.

## 类型选择

| 当前问题 | Archify 类型 | 主要关系 |
|---|---|---|
| 组件, 所有权, 信任区或模块边界是什么 | `architecture` | 组件与依赖 |
| 一项工作如何经过角色, 工具, 判断和回退 | `workflow` | 步骤与责任 |
| 一次调用或运行按什么顺序发生 | `sequence` | 参与者与消息 |
| 数据如何变换, 传递, 持有和消费 | `dataflow` | 数据契约与流向 |
| 对象或任务如何在状态间迁移 | `lifecycle` | 状态与事件 |

类型选择服从问题. 同一任务可以在不同问题下使用不同类型, 每份 IR 只回答一个主要问题.

## 算法推演

用 `workflow` 表达条件, 循环和 fallback. 用 `dataflow` 表达中间值, 变换和不变量. 用 `sequence` 表达算法与外部系统之间的时序.

先把输入条件, 决策点, 状态变化和输出条件写入 IR. 随后运行最小的真实样例, 将实际分支和中间结果回填到对应关系. 失败轨迹保留原始输出锚点, 关系模型只记录从证据中得到的结论.

IR 用来暴露缺失分支, 隐含循环和无法同时成立的不变量. 代码修改仍落在源码和测试载体中.

## 运行观察与调试

用 `sequence` 组织调用时间线, 用 `lifecycle` 组织状态变化, 用 `dataflow` 组织数据或事件在各阶段的形态.

预期关系来自规格或代码锚点. 实际关系来自日志, trace, 调试器, profiler 或可重复运行. 两类关系使用不同标签或不同 IR 文件, 以便准确指出首次分歧的位置.

一次观察形成一个有界证据项: 输入, 环境或版本, 可见事件, 原始输出位置. Archify 负责连接这些证据项, 原始工具负责证明它们.

## 业务流程与人机边界

用 lane 或 state 分开用户, Agent, 工具, 外部系统和持久化载体. 明确表达谁提供输入, 谁拥有最终决定, 哪一步需要授权, 哪一步产生外部副作用, 哪个结果返回给人类.

用户目标和业务规则是约束. Agent 的选择是推演. 工具返回是观察. 产物或外部变化是执行结果. IR 让四种内容保持可区分.

流程改变时只更新受影响的边界和关系. 直接的人机问答保持在对话中, 只有会影响多步执行的边界进入 IR.

## Git 与变更整理

Git 提供提交, 分支, diff 和作者化历史. clean-tools 或 CodeGraph 提供代码符号与影响关系. Archify 将这些事实组织成模块变更图, 发布流程, 交接路径或审查边界.

`compare architecture` 接收两份已经验证的 architecture IR, 并生成作者化 Architecture Delta. 它表达两份模型的差异. Git 操作和运行时影响由 Git 与代码分析工具给出.

## Skill 制作与使用

创建 skill 时, 用 `workflow` 检查触发, 路由, 工具选择, 权限边界, fallback 和输出. 用 `lifecycle` 检查 skill 从发现, 载入, 执行, 等待到完成或停止的状态. 用 `architecture` 检查 skill, 独立工具, Manager 和项目 adapter 的模块边界.

使用 skill 时, IR 可以成为任务内的工作记忆. 真实请求的行为验证仍检查实际工具调用, 产物和副作用. 模型中缺失的边表明说明或工具接口需要补充, 现实中不存在的边从模型中移除.

## 专业格式的解析梯度

发现成熟开源工具时, 先用该工具解析专业格式. Archify 组织测试输入, 预期结果, 实际结果和可用性判断.

现有工具无法满足项目与版本要求时, 读取目标引擎源码建立反序列化路径. 随后按具体项目, 引擎版本和当前工作生成 adapter skill 或脚手架.

可解析代码进入 CodeGraph 或 clean-tools 的精确事实层. 节点流程, 蓝图关系和其他非代码结构进入 Archify 的关系层. 未解析区域保持诊断状态并保留证据来源.

## 收敛判断

IR 已能回答当前问题, 未知项拥有明确来源, 下一步可以直接执行时, 停止扩张模型.

新节点只在它改变选择, 责任, 状态, 数据流或证据判断时加入. 视觉装饰, 重复事实和纯文字摘要留在最终说明中.
